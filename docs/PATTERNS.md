# Authoring patterns

Patterns compose Canon components into application layouts, sections and pages: dashboards, settings, list/detail views, onboarding, auth screens and similar app tasks. New catalog patterns should serve application development. The schema retains other category values, but their presence does not expand this contribution scope to marketing websites or email.

Create `src/patterns/<slug>.ts` and export a `Pattern` using `import type { Pattern } from '../types.ts'`. [`src/types.ts`](../src/types.ts) is the schema source of truth. Read [`dashboard-page.ts`](../src/patterns/dashboard-page.ts), [`settings-page.ts`](../src/patterns/settings-page.ts) and the helpers in [`_app.ts`](../src/patterns/_app.ts) for existing compositions.

## File contract

| Field | Authoring contract |
| --- | --- |
| `name`, `slug` | A clear name and unique kebab-case slug matching the filename. |
| `category` | Use `app-layout`, `app-section` or `app-page` for new application patterns. |
| `description` | Describe the user task, arrangement and when an agent should choose it. |
| `rules` | Concrete guidance on structure, spacing, copy, responsive layout and required application behavior. |
| `html` | The complete primary HTML fragment. |
| `variants` | Optional complete alternatives, each with a title, HTML and an optional description explaining the difference. |
| `css` | Optional pattern-specific layout CSS using tokens and the `cn-` prefix. |
| `viewport` | Optional `desktop`, `mobile` or `both` preview hint; review both widths when the pattern supports them. |

[`src/patterns/index.ts`](../src/patterns/index.ts) discovers sibling modules with its own extension (`.ts` in source, `.mjs` when compiled), excluding `index` and filenames starting with `_`. It collects exported objects with `slug` and `html` fields and sorts them by category, then slug. Keep one pattern per file and helpers in `_` modules; no manual registration is needed.

## Compose existing components

Reuse the anatomy and allowed prop values from component specs. Use the [component authoring guide](AUTHORING.md) when a shared component itself needs a change. Pattern CSS should style the layout around components rather than redefine their appearance.

The layout primitives are generated by `baseCss` in [`src/engine.js`](../src/engine.js):

| Primitive | Typical controls |
| --- | --- |
| `.cn-section`, `.cn-container` | `data-padding`, `data-bg`; container `data-size`. |
| `.cn-stack`, `.cn-row` | `data-gap`, `data-align`; row `data-justify`, `data-wrap` and `data-stack`. |
| `.cn-grid`, `.cn-split` | Grid `data-cols`, `data-gap`, `data-keep`; split `data-ratio`, `data-align`. |
| `.cn-center`, `.cn-measure`, `.cn-mx-auto`, `.cn-flex-1` | Alignment, readable width and flexible space. |
| `.cn-hide-mobile`, `.cn-show-mobile` | Responsive visibility with an equivalent usable path at each width. |
| `.cn-text-<style>`, `.cn-sr-only` | Composite typography and visually hidden accessible text. |

Use the supported attribute values in the engine; not every spacing token is a layout attribute value. The [`_app.ts`](../src/patterns/_app.ts) helpers include `SIDEBAR`, `PAGE_HEADER`, `CARD`, `TEAM_TABLE`, `STAT`, `TABS`, `FIELD` and `INPUT`. Helpers using `.cn-app*` classes need the matching `APP_CSS` in the pattern's `css`, as existing app pages demonstrate. A helper produces markup, not application state or event handlers.

Add CSS only for layout that components and primitives cannot express. Scope new classes to the pattern slug, for example `.cn-workspace-page__main`, and use `{token.path}` references for visual values. Use role-based radius tokens such as `{radius.card}` and keep control styles in the component. For responsive overrides, use a token breakpoint such as `@media (max-width: {breakpoint.md})`. Keep fixed or sticky layers inside the intended preview or application container.

Keep layout declarations in CSS or primitives. Inline styles are appropriate for data-driven geometry, demo media dimensions or an explicitly supported custom property; avoid inline color, typography or spacing overrides. In authored HTML or SVG, token values use `var(--cn-...)`; `{...}` references are resolved in the pattern's CSS. Both markup and CSS use the canonical `cn-` prefix so generation can replace it.

## Make each example useful

- Provide a standalone fragment for the primary layout and every variant. A page includes its shell and content; a section includes enough context to demonstrate its task.
- Give variants a meaningful structural or workflow difference. Show complete markup for a selected detail pane, empty state or validation step. Changing an attribute or color on the same skeleton does not demonstrate those states.
- Use realistic English copy and fictional product data. Prefer inline SVG or local assets over remote images, with descriptive alternatives for meaningful visuals.
- Preserve landmarks and heading order: one `h1` for a full page, descriptive section headings and labelled navigation. Give controls accessible names, unique IDs and correct current, expanded or selected states.
- Describe interaction responsibilities in `rules`: routes, validation, keyboard navigation, focus restoration, async loading and error handling where relevant. Static examples and flow variants do not implement these behaviors.
- At phone widths, make actions reachable, allow appropriate wrapping, and contain table or pane scrolling. Hiding a desktop control requires an accessible way to complete the same task.

## Verify the contribution

Use [the temporary preview workflow](../CONTRIBUTING.md#preview-in-a-temporary-workspace). A fresh `init` copies the current pattern catalog, validates the system and builds Studio. A later `build` works from that JSON snapshot, so reinitialize into a new temporary directory after editing catalog source.

Open the pattern at `#p-<slug>` in Studio. Check the primary layout and every variant at desktop (1280px) and mobile (375px), in light and dark themes, and with the workflow's custom prefix. Inspect overflow, long content, labels, focus visibility and the behavior of any native controls. Include screenshots of the affected layouts in the pull request.

Run `npm run test:ci` before requesting review. Review the generated pattern CSS and reference documentation as well as the preview. The validator checks pattern CSS token references; it does not establish that pattern HTML, accessibility or application interactions are correct.
